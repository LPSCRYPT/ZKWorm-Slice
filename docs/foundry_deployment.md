# Foundry deployment and verification

This slice includes a self-contained deployment script for the v7 Solidity verifier generated by `bb write_solidity_verifier`.

The script intentionally generates one verifier project per variant under `generated/foundry_<variant>/`. Barretenberg emits generic Solidity symbol names (`HonkVerifier`, `Honk`, `FrLib`, etc.), so compiling both generated verifiers in the same Solidity source tree causes duplicate-symbol conflicts. Separate generated Foundry projects keep the generated code unmodified and auditable.

## Localhost

Terminal 1:

```sh
anvil --code-size-limit 1000000
```

Terminal 2:

```sh
export PRIVATE_KEY=0xac0974bec39a17e36ba4a6b4d238ff944bacb478cbed5efcae784d7bf4f2ff80
python3 scripts/deploy_and_verify.py --variant poseidon --rpc-url http://127.0.0.1:8545
python3 scripts/deploy_and_verify.py --variant open --rpc-url http://127.0.0.1:8545
```

Each invocation:

1. Ensures the Noir proof artifacts exist.
2. Generates the Solidity verifier from the variant verification key.
3. Builds the generated Foundry project.
4. Deploys the verifier.
5. Executes a `cast call` verification.
6. Sends an actual verification transaction.

## Base Sepolia

Set an RPC URL and funded private key, then run:

```sh
export RPC_URL=https://sepolia.base.org
export PRIVATE_KEY=<funded-private-key>
python3 scripts/deploy_and_verify.py --variant poseidon
python3 scripts/deploy_and_verify.py --variant open
```

The generated verifier is near the EIP-170 contract-size limit and dynamically links `ZKTranscriptLib`; the script handles the library deployment/linking automatically. The open-output verifier also carries a much larger public-input array than the Poseidon verifier. If a public RPC rejects the open transaction due to gas/size policy, the Poseidon path is the lower-cost POC path and the open path can be run against an RPC provider with higher transaction simulation limits.
